# 非凡之爱：已验证的问题与修复

适用于本模板的试片、失败诊断和断线恢复。不把一次角色外貌或创作取舍升级成全部视频的规定。

## 减少无效尝试

先做003男单人、004女单人、015双人近景三路身份试片，尤其检查015是否仅换衣而仍是源演员；未通过前不展开同类重做。并行候选要有可诊断差别，例如精简身份定义、消除服装冲突、改用临时头部软化运动引导。单纯加词、同义改写或升一采分辨率多次没有解决015原脸残留。

上传缓存按文件内容SHA256校验，不能只用同一路径复用旧上传；覆盖参考图或运动输入后须重新上传。旧缓存没有哈希也重新上传媒体，不复用来源不明的缓存。每个受理任务记录实际输入哈希和提示词哈希，不记录Key。

脸换对后再修服装，可用时间正确的成功结果做后续运动引导，避免反复从原脸输入重新开始。所有衍生输入记父文件哈希，原视频和参考图只读。视觉修复无固定三次上限，但同原因无改善就换策略；提交、权限、余额和执行失败先诊断，不盲目自动付费重提。

## 012–015：衣物交接与遮挡

013 实际出现过：修复披衣归属的候选 `wrap_owner` 保住披衣，却在整段漏掉一号并让二号撑伞；只核对披衣导致误选。原始主候选在溅水阶段保留两人、一号撑伞，但披衣在镜头前后不连续。先把两人、撑伞者、站位、衣物和动作作为同一段的联合验收条件；每次改任一项后，逐段复查全部条件。无完美候选时保留可追溯预览并如实标明取舍，不能宣称全部通过。仅本项目的一号/二号映射随用户参考图变化，不将某次角色外观写成固定人物。

007 的包内镜头方向说明与解码画面不一致，站位应以原始视频逐帧为准。012 的空街不得补路人。009 短肢参考与源伞动作重叠时，局部运动引导比反复同义改词更有效，但必须核对嘴部和两个人。

002 源片伞本身有快速运动，二次引导可能将遮挡变成涂抹，不把模糊脸判通过。011 静态修手引导叠在运动中的脸部时曾产生双重五官；避免遮罩覆盖脸并逐帧检查，光流插帧也可能产生重影。017 补手的引导线可能直接进入成片，检查原尺寸的手、伞和背景边缘及连续帧。

012男角色交出外衣后，013–015不能让两人各穿一份相同外衣。先列本次角色外层/内层状态，同时更新Subject定义、retention和动作句，不能再泛写完整参考服装始终保留。本次灰色内衣、绿色外袍只是实例，下次按新参考图推导，不写死颜色款式。

男头的源红花应固定到目标头发上，走位、溅水和伞遮挡后仍在。014伞约0.50秒抬起时复核脸、发饰和红花；013宽景还要看女角色完整长发和鞋，不能留下源女短发/高跟鞋。

015多次纯提示词和升分辨率仍保留原长鼻、下颌、乱发或凸眼。避免歧义句 `Do not substitute the original people`。每拍以目标脸型、正常虹膜、眉鼻嘴下巴和发型为正向身份，完整原脸区域都须替换。

## 015身份恢复：可执行的离线引导

参考图/映射无误、精简提示词仍有明确原脸时使用。只适配固定015源视频，脚本校验源哈希，不能套给其他视频：

```text
python <技能目录>/scripts/prepare_identity_guide.py --project <工作副本> --name head_rebuild --prompt <为本次人物写好的015提示词.txt> --radius 70
```

它只准备 `candidates/015/head_rebuild`：73帧、24fps、原动作/机位和原段音轨，仅软化运动输入副本中的原头纹理。用户身份图直接复制，绝不裁改。先看guide截图再提交；提示词说明临时软化区域必须恢复为清晰目标脸，最终不能交付模糊头或引导遮罩。

红花保留掩码须限定红色和位置。宽泛的“偏红像素都保留”曾同时保留原肤色、嘴和鼻；脚本已用严格红色条件修正。

## 缺音轨导致任务失败

无音轨副本曾让H3节点302报 `KeyError: waveform`，外层只返回“工作流运行失败”。所有运动引导必须重新映射原段音轨；运行器在上传/付费前检查视频+音频、24fps、准确帧数及≤10秒。交付音乐与生成输入音轨分开管理。

## 手部及后处理

原包015有全遮手要求，本次原动作却是自然扶手。强制全遮出现过多手、布料块和异常遮挡，制作最终采用自然扶手并告知用户。不能把本次取舍当成以后所有角色的同意；按本次要求、参考服装和源动作决定。用户明确要全遮时不能悄悄改露手，需继续修或给可审阅选项。

肤色阈值调色出现过矩形边界、拇指色块、斑点及木伞柄误染。原尺寸检查所有保留帧和相邻帧，不能只看单帧。掩码不连续或误伤道具时，保留稳定自然阴影并说明选择；失败调色版不得入选片。

## 共享队列与下载恢复

- 本次最多3个生成槽位，主批与候选合计；同Key其他聊天计入服务端真实总量。上限动态读取，不写死成曾观察到的5，也不因外部任务超过3而永远不补交。
- 容量满15秒只读查询；真实421共享60秒提交冷却。成功但下载中的worker不占生成槽位。已选段的未受理备选及时移出计划；已受理任务保留溯源。
- 重启先读任务ID、选片及锁PID，接管worker，不重跑主批、不删状态、不杀其他聊天进程。主批尚有未受理段时不与修复控制器竞争提交。
- SUCCESS缺地址继续查原任务，下载失败只补下载，不改FAILED以触发重付费。提交回执不确定冻结新提交并查提供方记录。
- 本地worker启动只代表开始等待或准备，只有服务端返回taskId才算已受理。状态文件原子写入遇到权限错误时先确认是否已经受理，不声称提交成功，也不盲目重试付费任务。
- 本机COS曾因系统DNS出现TLS EOF。运行器保留证书校验，用短时已验证IP缓存、HTTPS DoH及curl `--resolve` 恢复；不关闭TLS校验、不改系统DNS。下载先写.part，再原子落盘；路由失败不重生成。

耗时分开记录提交前空位等待、接口受理后的生成/排队、下载以及质检返工；没有提供方有效计时字段时，不能把“受理到下载”的总耗时声称为纯模型推理耗时。
